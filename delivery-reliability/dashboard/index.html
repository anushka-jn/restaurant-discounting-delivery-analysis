Limitations

  • The promised ETA isn't in this data. Only actual delivery time is recorded, so this measures duration, not whether a promise was broken. The honest next step is instrumenting the quoted ETA, not more analysis of this file.
  • It's a single ~44-day snapshot — seasonal effects (e.g. monsoon weather codes, a festival cluster) can't be separated from structural ones with one window.
  • Distance is derived from raw lat/lon that needed correction. ~400 rows carried a sign-flipped latitude (fixed with ABS()); the haversine distance is straight-line, not actual road distance, so it understates real travel distance especially in dense urban grids.
  • "City" here is the rider's home-base code parsed from their ID (e.g. INDORES19DEL02 → Indore), not a verified order-level city field — a reasonable proxy, not ground truth.
Pipeline: DuckDB SQL (staging → cleaning → haversine/pickup-delay/daypart feature engineering → analysis). Every measure here is P90 or median, never a plain average, because reliability is a tail problem. Full SQL and cleaned tables in sql/ and data/processed/.
